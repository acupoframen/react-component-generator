# Commit

## 1. 변경사항 분석

- 현재 작업 디렉터리를 기준으로 Git 저장소와 적용되는 `AGENTS.md` 등 저장소 지침을 확인한다. 저장소가 아니면 이유를 알리고 중단한다. 임의로 `git init`을 실행하지 않는다.
- `git status --short`, `git diff`, `git diff --cached`로 미스테이징·스테이징 변경을 모두 확인한다. 새 파일은 diff에 나오지 않으므로 상태 목록에서 찾아 내용을 확인한다.
- 변경이 없으면 커밋할 내용이 없다고 알리고 종료한다. 충돌이 있으면 해결이 필요함을 알리고 커밋을 중단한다.
- `.env`, API 키 등 비밀정보와 불필요한 빌드 산출물은 커밋 대상에서 제외한다. 비밀값을 출력하지 않는다.

## 2. 논리적 단위 분류

- 같은 목적의 구현·관련 테스트·문서는 하나로 묶고, 독립적인 목적의 변경은 별도 커밋으로 나눈다. 파일별로 기계적으로 분리하지 않는다.
- 사용자가 지정한 범위를 우선한다. 기존 스테이징 내용도 분석하되 관련 없는 변경을 자동으로 포함하거나 해제하지 않는다.
- 한 파일에 여러 목적의 변경이 섞여 있으면 부분 스테이징으로 분리할 수 있는지 확인한다. 서로 의존해 분리가 어렵다면 함께 묶고 이유를 간단히 알린다.

## 3. 한국어 커밋 메시지 작성

형식은 `type: 한국어 요약`이며 다음 유형 중 변경 목적에 맞는 것을 선택한다.

| 유형 | 기준 |
|---|---|
| `feat` | 사용자에게 제공하는 기능이나 UI 추가·개선 |
| `fix` | 잘못된 동작 수정 |
| `refactor` | 동작을 유지하는 코드 구조 개선 |
| `chore` | 설정·의존성·개발 도구·문서 등 유지보수 |

요약은 무엇이 달라졌는지 구체적으로 작성한다. 예: `feat: 레트로 테마와 반응형 작업대 적용`.

## 4. 별도 승인 없이 커밋

- 사용자의 커밋 요청을 해당 범위의 스테이징·커밋 권한으로 보고, 메시지나 분할 계획에 대한 추가 승인을 요청하지 않는다. "모든 변경사항" 요청은 제외 대상 외의 전체 변경을 포함한다. 사용자가 별도로 검토나 승인을 요구했다면 그 지시를 따른다.
- 커밋별 핵심 범위와 메시지를 간단히 알리고 필요한 저장소 검증을 마친 뒤 바로 진행한다.
- 작업 중 파일이 바뀌었다면 diff를 다시 확인하고 요청 범위 안에서 분류와 메시지를 조정한다. 요청 범위를 넘어서는 변경을 임의로 포함하지 않는다.
- `git add -- <대상 경로>` 또는 부분 스테이징으로 요청 범위의 변경만 선택한다. 무차별적인 `git add .`은 사용하지 않는다. 기존 스테이징에 범위 밖 변경이 있으면 이를 보존하면서 분리할 수 있는 방법을 사용하고, 안전하게 분리할 수 없다면 해당 커밋을 중단하고 이유를 알린다.
- 각 커밋 직전 `git diff --cached`로 해당 커밋 내용이 의도한 단위와 일치하는지 확인한다. 요청 범위 밖 변경이 포함되어 있으면 커밋하지 않는다.
- 작성한 한국어 메시지로 `git commit`한다. 여러 줄 메시지는 임시 UTF-8 파일에 작성하고 `git commit -F <파일>`로 전달한다.
- 훅이나 검증 실패 시 이유를 알린다. 훅 우회, 자동 수정에 따른 범위 확대, 반복 커밋 시도는 하지 않는다. 수정이 필요하면 수정·검증 후 변경된 계획을 제시한다.
- 완료 후 커밋 해시·메시지와 `git status --short` 기준 남은 변경을 보고한다. 여러 커밋 중 일부만 성공했다면 성공한 커밋과 중단 지점을 구분한다.
- 별도 요청 없이 push, amend, reset 또는 기존 커밋 재작성은 수행하지 않는다.
